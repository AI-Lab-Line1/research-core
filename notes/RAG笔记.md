## 一、核心动机

### 1.1 大模型的原生局限

LLM 的参数化知识存在三个根本问题：

| 问题                 | 表现                          | 后果                        |
| -------------------- | ----------------------------- | --------------------------- |
| **知识截止**   | 训练数据有截止日期            | 无法回答新事件              |
| **幻觉**       | 模型会编造事实                | 高风险管理场景不可接受      |
| **数据稀疏**   | 长尾知识训练不足              | 专业领域表现差              |
| **上下文限制** | 模型一次能读取的内容有上限    | 长文档/多文档场景内容被截断 |
| **推理成本**   | 输入 token 越多，推理成本越高 | 全量注入文档不经济          |
| **推理速度**   | 输入越长，首 token 延迟越大   | 实时场景响应慢              |

### 1.2 RAG 的解决思路

```text
不依赖模型「记住」所有知识，而是在每次回答前：

  用户提问 → 从知识库检索相关文档 → 文档 + 提问 → LLM 生成回答
                   ↑                          ↑
            外部知识库                    上下文增强
```

**关键洞察**：RAG 把「记忆」从模型参数中解耦出来，放到可独立更新、可追溯来源的外部知识库中。

### 1.3 与微调（Fine-tuning）的对比

| 维度       | RAG                       | 微调         | 备注                              |
| ---------- | ------------------------- | ------------ | --------------------------------- |
| 知识更新   | 替换索引即可              | 重新训练     | RAG 秒级更新                      |
| 幻觉控制   | 强（有原文约束）          | 弱           | RAG 可追溯到源文档                |
| 领域适配   | 依赖语料库质量            | 依赖标注数据 |                                   |
| 推理延迟   | 增加检索时间（~50-500ms） | 无额外开销   |                                   |
| 上下文窗口 | 受限于 LLM 上下文长度     | 无额外开销   | 长上下文模型降低了 RAG 的截断压力 |
| 可解释性   | 强（可展示检索到的原文）  | 黑箱         |                                   |

**实际组合使用**：

- 微调让模型掌握领域格式/语气/特殊指令
- RAG 提供具体的领域事实

### 2.2 三阶段划分

```text
索引阶段（Indexing）         检索阶段（Retrieval）          生成阶段（Generation）
───────────────────         ──────────────────            ──────────────────
文档清洗                       ① 召回粗筛                    上下文注入
分块策略                       查询向量化                     Prompt 构造
Chunk Embedding               向量相似度匹配                  LLM 生成
存入向量库                     Top-K 粗筛                    输出后处理
（存向量 + 存原文）             余弦/欧氏/点积
                               │
                               ② 重排精筛
                               Cross-Encoder 逐对评分
                               精挑细选 Top-N
                               结果合并去重
```

> **注意**：索引时，文本 Embedding 变成**向量**后存入向量数据库，同时**原始文本也会一并存储**。检索时通过向量相似度找到匹配的向量，返回对应的原始文本片段——向量负责"定位"，原文负责"理解"。

## 三、检索模块详解

检索是 RAG 的核心瓶颈。检索质量直接决定生成质量。

### 3.1 文档分块（Chunking）

分块大小和策略是 RAG 最重要的工程决策之一。

| 策略                   | 方法                                    | 优势           | 劣势           | 适用场景   |
| ---------------------- | --------------------------------------- | -------------- | -------------- | ---------- |
| **固定长度**     | 按 token/字符数切分                     | 简单、可预测   | 切断语义单元   | 通用场景   |
| **递归分割**     | 按段落→句子→子句层级回退              | 保留语义完整性 | 块大小不均匀   | 结构化文档 |
| **语义分割**     | 在语义边界处切分（如 embedding 突变点） | 语义完整性高   | 计算开销大     | 长文档     |
| **基于文档结构** | 按 Markdown 标题 / HTML 标签 / PDF 章节 | 自然边界       | 依赖格式一致性 | 结构化内容 |
| **Agent 式分割** | LLM 判断块边界                          | 质量最高       | 慢，成本高     | 高价值场景 |

**经验法则**：

```text
分块大小的权衡：

块太小（<100 tokens）：
  ✓ 精确匹配概率高
  ✗ 上下文不完整，缺少全局信息

块太大（>1000 tokens）：
  ✓ 上下文完整
  ✗ 噪声多，语义被稀释
  ✗ 超过向量检索的有效区分粒度

常见默认：256-512 tokens，带 10-20% 的重叠（overlap）
```

### 3.2 分块重叠（Chunk Overlap）

```text
无重叠：
  [段落A       ] [段落B       ] [段落C       ]
  边界处信息丢失

有重叠（10-25%）：
  [段落A+           ] [段落A尾+B头+          ] [段落B尾+C头+    ]
                     ↑ 边界的上下文保留
```

- 重叠比例一般 10%~25%
- 过长重叠会让向量索引中大量冗余向量，降低检索精度

### 3.3 向量化（Embedding）

#### 3.3.1 常用的 Embedding 模型

| 模型                            | 维度 | 上下文长度 | 特点                                                                                                      |
| ------------------------------- | ---- | ---------- | --------------------------------------------------------------------------------------------------------- |
| text-embedding-3-small (OpenAI) | 1536 | 8191       | 性价比高，可降维                                                                                          |
| text-embedding-3-large (OpenAI) | 3072 | 8191       | 精度最高                                                                                                  |
| bge-large-zh-v1.5 (BAAI)        | 1024 | 512        | 中文最强                                                                                                  |
| bge-m3 (BAAI)                   | 1024 | 8192       | 多语言 + 多粒度                                                                                           |
| jina-embeddings-v3              | 1024 | 8192       | 多语言、可任务指定                                                                                        |
| gte-Qwen2 (Alibaba)             | 4096 | 8192       | 开源中文 SOTA                                                                                             |
| voyage-2 (VoyageAI)             | 1024 | 16000      | 长上下文                                                                                                  |
| **MTEB 排行榜**           | —   | —         | 选型参考：[https://huggingface.co/spaces/mteb/leaderboard](https://huggingface.co/spaces/mteb/leaderboard) |

> Embedding 模型选择可以参考 MTEB Leaderboard，关注分类、聚类、检索等不同任务的得分。中文场景建议额外关注 C-MTEB。选型时优先使用与检索任务匹配的模型。

#### 3.3.2 查询与文档的编码差异

很多生产系统的经验是：查询和文档应使用不同的编码策略。

```text
原因：
  - 查询短（几词到一句话），文档长（几百 token）
  - 短文本和长文本的语义分布在 embedding 空间中不同

优化方案：
  1. Query 端加前缀模板（如引号模式下 bge 的 'Represent this sentence for searching relevant passages: '）
  2. 用混合检索（dense + sparse）互补
  3. 查询改写（HyDE 见 9.2 节）将查询扩展为伪文档再检索
```

### 3.4 相似度度量

| 度量       | 公式                                                                                                 | 取值范围  | 适用场景                       |
| ---------- | ---------------------------------------------------------------------------------------------------- | --------- | ------------------------------ |
| 余弦相似度 | $\cos(\mathbf{a}, \mathbf{b}) = \frac{\mathbf{a} \cdot \mathbf{b}}{\|\mathbf{a}\| \|\mathbf{b}\|}$ | [-1, 1]   | 最常用，与向量范数无关         |
| 欧氏距离   | $\|\mathbf{a} - \mathbf{b}\|_2$                                                                    | [0, ∞)   | 向量已经 L2 归一化时与余弦等距 |
| 点积       | $\mathbf{a} \cdot \mathbf{b}$                                                                      | (-∞, ∞) | 向量已经归一化时等价于余弦     |

> 实际上，如果 Embedding 向量做了 L2 归一化，余弦相似度和点积是等价的。

### 3.5 召回（Retrieval）与重排（Rerank）

召回和重排是检索阶段的两步走策略，二者的核心区别在于**计算方式不同**：

```text
                    召回（Retrieval）              重排（Rerank）
                    ────────────────              ────────────────
  编码方式          Bi-Encoder                    Cross-Encoder
                    Query 和 Doc 各自独立编码      Query 和 Doc 拼接后一起输入
  计算方式          向量距离（余弦/欧氏/点积）      逐对交互计算评分
  能否预先索引       ✓  可以                        ✗  不可以
  成本              低                            高
  速度              快                            慢
  准确率            低                            高
  适用场景          海量文档快速粗筛 Top-K          少量候选精排 Top-N
```

**为什么"先召回再重排"而不是直接精排？**

因为召回（Bi-Encoder）可以**预先计算并索引**所有文档向量，检索时只需将 Query 编码一次，通过 ANN 索引在毫秒级完成海量匹配。代价是 Query 和 Document 之间没有交互，精度有限。

重排（Cross-Encoder）将 Query 和每个 Document **拼接后一起编码**，能捕捉词级别的精确匹配关系，精度远高于 Bi-Encoder。但**无法预先索引**，必须对每一对实时计算，复杂度 O(N)。因此只能在小规模候选集上操作。

**工程实践**：召回时放大 Top-K（如 K=50~100），宁可多召回一些噪声；再用 Cross-Encoder 重排精挑 Top-N（如 N=3~5）送入 LLM。常用重排模型：bge-reranker-v2-m3、Cohere Rerank、Jina Reranker。

### 3.6 混合检索（Hybrid Search）

单一向量检索在以下场景容易失败：

```text
场景 1：专有名词 → "CRISPR-Cas9"
  向量检索可能匹配到"基因编辑"（语义相似但不够精确）
  关键词检索能精确命中"CRISPR-Cas9"

场景 2：简称/缩写 → "NLP"
  向量检索可能匹配到其他领域
  关键词检索可以配合词表

场景 3：高频泛化 → "应用程序"
  向量空间中被过度泛化
  精确匹配更有用
```

**混合检索策略**：

```text
密集检索（Dense Retrieval）       稀疏检索（Sparse Retrieval）
    │                                  │
    │  embedding 向量 × 余弦距离        │  BM25 / TF-IDF 文本匹配
    │                                  │
    └──────────────┬───────────────────┘
                   │
                   ▼
          ┌──────────────────┐
          │  分数融合（Fusion）  │
          │                    │
          │  RRF 融合：         │
          │  score = Σ 1/(k + rank_i)    │
          │                    │
          │  ⚠️ 注意分布不一致：        │
          │  两套分数范围/分布完全不同    │
          └──────────────────┘
```

**RRF（Reciprocal Rank Fusion）**：

$$
\text{RRFScore}(d \in D) = \sum_{r \in R} \frac{1}{k + r(d)}
$$

- $R$ 是所有检索方法的结果集
- $r(d)$ 是文档 $d$ 在某个检索方法中的排名
- $k$ 是平滑常数（通常 60），防止排名极端

## 四、检索质量评估

### 4.1 检索评估指标

| 指标                  | 说明                     | 公式                                                               |
| --------------------- | ------------------------ | ------------------------------------------------------------------ |
| **Recall@K**    | Top-K 中相关文档的比例   | $\frac{\text{相关文档在 Top-K 中的数量}}{\text{全部相关文档数}}$ |
| **Precision@K** | Top-K 中相关文档的比例   | $\frac{\text{相关文档在 Top-K 中的数量}}{K}$                     |
| **MRR**         | 第一个相关文档的位置     | $\frac{1}{N} \sum \frac{1}{\text{rank}_i}$                       |
| **NDCG@K**      | 考虑排序位置的归一化指标 | 基于累积增益折扣                                                   |
| **MAP**         | 平均精度均值             | 对所有 query 的 AP 取平均                                          |

### 4.2 检索失败的典型情形

```text
Query: "Transformer 自注意力机制的计算复杂度是多少？"

检索到的 Top-5 Chunks：
  #1  "自注意力机制允许每个位置关注所有位置..."      ← 语义相关但无复杂度
  #2  "Transformer 由编码器和解码器组成..."          ← 完全无关
  #3  "多头注意力将 QKV 投影到多个子空间..."         ← 边缘相关
  #4  "复杂度为 O(n²·d)，其中 n 是序列长度..."       ← ✅ 正确答案
  #5  "BERT 使用掩码语言模型进行预训练..."            ← 完全无关

问题：如果 K=3，正确答案在第 4 位 → 丢失
解决方案：
  - 增大 K（但会引入更多噪声）
  - 优化分块策略让关键信息更靠前
  - 加 reranker 重新排序
```

### 5.2 Prompt 模板设计

Prompt 设计对生成质量影响极大。

#### 模板 1：基础注入

```text
请基于以下文档内容来回答问题。如果你不知道答案，请直接说不知道，不要编造信息。

文档内容：
{context}

问题：{query}
回答：
```

#### 模板 2：带引用

```text
请根据以下文档回答用户问题。在回答末尾标注信息来源编号。

文档：
[1] {chunk_1}
[2] {chunk_2}
[3] {chunk_3}

问题：{query}

回答要求：
- 如果文档中有相关信息，请基于文档回答并标注引用编号
- 如果文档中没有相关信息，请明确说 "根据提供的文档，没有找到相关信息"
- 不要混合不同来源的文档信息，除非它们互相支持
```

#### 模板 3：结构化输出

```text
你是一个问答助手。你的任务是：

1. 阅读以下文档片段
2. 回答用户的问题
3. 你的回答需要包含 "答案" 和 "引用来源" 两个部分

文档：
{context}

问题：{query}

按以下 JSON 格式输出：
{
  "answer": "你的回答",
  "confidence": "high/medium/low",
  "sources": ["来源1", "来源2"]
}
```

### 5.3 上下文窗口管理

长上下文模型（GPT-4-128K, Claude-100K, Gemini-1M）改变了 RAG 的工程决策：

```text
短上下文模型时代（~4K tokens）：
  - 必须精心挑选 Top-K
  - K 值受限（通常 3-5）
  - chunk 大小受限（~512 tokens）

长上下文模型时代（128K-1M tokens）：
  - 可以注入更多 chunk（K=20+, 甚至全量注入）
  - 检索作为「排序」而非「筛选」
  - 仍然需要注意：中间信息丢失（Lost in the Middle）
```

**Lost in the Middle 问题**（Liu et al., 2023）：

```text
模型对上下文不同位置的关注度：

位置：   开头 ██████████░░░░░░░░░░░░░░▒▒▒▒▒▒███ 结尾
准确率： 高                             下降      略有回升
        ↑                                ↑        ↑
      Primacy Effect               Recency Effect

结论：最相关的文档放在开头和结尾，中间放次要文档。
```

## 六、RAG 评估体系

### 6.1 评估维度

```text
RAG 系统评估 = 检索质量 + 生成质量 + 端到端质量

检索质量：
  ├── Recall@K / Precision@K
  ├── MRR / NDCG
  └── 检索延迟（P50/P99）

生成质量：
  ├── 忠实度（Faithfulness）— 答案是否忠于检索结果
  ├── 答案相关性（Answer Relevancy）
  └── 幻觉率（Hallucination Rate）

端到端质量：
  ├── 正确率（Accuracy）
  ├── 完整度（Comprehensiveness）
  └── 用户体验指标（如 Task Success Rate）
```

### 6.2 RAGAS 评估框架

RAGAS（RAG Assessment）提出了三个核心指标：

$$
\text{Faithfulness} = \frac{\text{从检索文档中可支持的陈述数}}{\text{总陈述数}}
$$

$$
\text{Answer Relevancy} = \frac{1}{|G|} \sum_{g \in G} \cos(\mathbf{e}_q, \mathbf{e}_g)
$$

其中 $G$ 是根据答案逆向生成的问题集合。

$$
\text{Context Precision} = \frac{\sum_{k=1}^K (\text{Precision@k} \times v_k)}{\text{总的} top-K \text{中文档数}}
$$

其中 $v_k$ 表示第 $k$ 个文档是否相关。

## 八、工程实践要点

### 8.1 检索优化清单

```text
□ 分块策略合理（文档结构 + 语义分割）
□ 分块重叠 10-25%
□ Top-K 值合理（5-15 根据上下文长度调整）
□ 混合检索（Dense + Sparse + RRF 融合）
□ 查询改写/扩展（减少 Query-Document 语义鸿沟）
□ Reranker 二次排序（减少 Top-K 噪声）
□ 去重过滤（相似 chunk 只保留一个）
□ 考虑时效性（时间衰减权重）
```

### 8.2 检索质量控制

```text
检索失败（Retrieval Failure）：
  - 原因：Query 和文档语义不对齐
  - 缓解：查询改写（HyDE）、多路检索

上下文溢出（Context Overflow）：
  - 原因：检索结果太多淹没关键信息
  - 缓解：Reranker、精排、自适应 K 值

信息冗余（Information Redundancy）：
  - 原因：多个 chunk 包含相同内容
  - 缓解：相似度阈值去重、MMR（最大边际相关性）

知识冲突（Knowledge Conflict）：
  - 原因：检索到矛盾信息
  - 缓解：置信度评分、多数投票、LLM 评判
```

### 8.3 生产环境监控

```text
关键监控指标：

检索层：
  - 检索延迟 P50/P99
  - 检索召回率（抽样评估）
  - 无结果率（Empty Response Rate）

生成层：
  - 忠实度评分（定期人工抽样）
  - Answer Relevancy 评分
  - 用户反馈（Thumbs up/down）

系统层：
  - 向量数据库连接状态
  - Embedding API 调用量/错误率
  - LLM API 成本
```

### 8.4 成本优化

```text
Embedding 成本：
  - 索引阶段：一次性，考虑用本地开源模型
  - 检索阶段：每次查询都调用，可缓存高频 Query

向量数据库成本：
  - 小数据集：FAISS + 文件存储（免费）
  - 中数据集：单机 Qdrant/Milvus
  - 大数据集：分布式 + 分片

LLM 成本：
  - 上下文越长 cost 越高
  - 控制注入的 chunk 数量和质量
  - 考虑用小模型做首轮过滤
```

## 九、进阶技术

### 9.1 查询改写（Query Rewriting）

```text
用户原始查询往往不适合直接用于向量检索：

  用户： "DeepSeek 和 Claude 比起来怎么样"
  改写： "DeepSeek vs Claude 模型对比分析 性能 价格 能力"

改写方法：
  1. LLM 改写（成本高但质量好）
  2. 规则改写（同义词替换、关键词提取）
  3. 多查询扩展（生成多个不同的检索 Query）
```

### 9.2 HyDE（Hypothetical Document Embeddings）

```text
核心思想：不直接检索查询，而是先用 LLM 生成一个假设性的理想文档，
然后用这个伪文档的 embedding 去检索真实文档。

流程：
  Query: "深度学习模型压缩的主要方法有哪些？"
    ↓
  LLM 生成伪文档: "深度学习模型压缩包括知识蒸馏、量化..."
    ↓
  用伪文档的 embedding 查询向量库
    ↓
  找到最相似的真实文档

优势：
  - 拉近 Query 和 Document 的 embedding 分布
  - 特别适合 Query 很短但文档很长的场景

劣势：
  - 增加一次 LLM 调用
  - 伪文档的质量依赖 LLM
```

### 9.3 迭代检索（Iterative Retrieval）

```text
单次检索的局限性：
  - 多跳问题需要多次检索
  - 第一次检索结果可能不足以回答问题

迭代检索流程（Self-Ask / Step-Back）：

  Q: "Transformer 在哪些 NLP 任务上表现最突出？"
    ↓
  检索 #1: "Transformer 架构..."
    → 未找到具体 task 列表
    ↓
  模型发现信息不足，生成子查询
    ↓
  子查询: "Transformer 在机器翻译和文本分类上的表现"
    ↓
  检索 #2: "...在 WMT 翻译任务上 BLEU 提升 4.2..."
    → 获取到具体任务表现
    ↓
  生成最终回答
```

### 9.4 层次检索（Hierarchical Retrieval）

```text
适用于长文档的场景：

文档层级：
  Chapter 1 ──────→ Section 1.1 ──→ Paragraph A ──→ Sentence 1
       │                 │               │
   摘要向量           段落向量         句子向量
   (粗粒度)          (中粒度)         (精粒度)

检索策略：
  1. 粗检索：在摘要层面找到相关章节
  2. 细检索：在相关章节内搜索段落
  3. 精检索：返回最相关的段落

优势：
  - 减少全局搜索空间
  - 保留层级上下文
```

### 9.5 Agentic RAG（基于 Agent 的 RAG）

```text
不再是被动的"检索→生成"线性流程，而是让 LLM Agent
自主决定何时检索、检索什么、如何组合信息。

典型工具箱：
  RAG Agent
  ├── Tools:
  │   ● Web Search        — 实时信息
  │   ● Vector Search     — 内部知识库
  │   ● SQL Query         — 结构化数据
  │   ● Code Interpreter  — 计算结果
  │   ● Read PDF          — 单文档精读
  └──

工作流示例：
  Q: "对比 2024 年 Q1 和 Q2 的销售数据，分析增长最大的产品线。"

  Agent 的思考链：
    1. "需要销售数据" → 调用 SQL Query 获取结构化数据
    2. "需要了解产品线定义" → 调用 Vector Search 查询产品文档
    3. "计算增长率" → 用 Code Interpreter 做计算
    4. "需要行业背景" → 调用 Web Search 搜索行业报告
    5. "生成综合分析报告"
```

### 9.6 多模态 RAG

```text
不仅检索文本，还检索图像、表格、代码等。

Pipeline：
  Query: "ResNet 的结构图是怎样的？"
    ↓
  多模态 Embedding 检索文本 + 图片
    ↓
  检索结果：
    [1] "ResNet 引入了残差连接..."              ← 文本
    [2] [ResNet 架构图]                        ← 图片
    [3] "ResNet-50 各层参数数量表"              ← 表格
    ↓
  多模态输入 → 多模态模型生成回答（含图文）

关键挑战：
  - 不同模态的统一表示
  - 跨模态对齐
  - 多模态结果的排序和融合
```

### 9.7 Graph RAG（知识图谱增强 RAG）

```text
传统向量检索的局限：每个 chunk 独立编码，丢失了文档之间的结构关系和跨文档关联。

Graph RAG 在向量检索之外，引入图结构来组织知识：

知识图谱构建：
  原始文档 ──→ 实体抽取（LLM/NER）──→ 关系抽取 ──→ 图谱构建
                    ↓                          ↓
              节点（实体）                  边（关系）
                    ↓                          ↓
              实体 Embedding              关系类型编码

检索流程：
  Query: "Transformer 的发明对哪些后续模型产生了影响？"

  ① 向量检索找到相关文档 chunk（传统 RAG）
  ② 从 chunk 中提取关键实体 → 在图谱中定位节点
  ③ 图遍历：沿关系边扩展（一跳、两跳...）
  ④ 汇总路径上的相关信息
  ⑤ 将图结构信息 + 检索结果一并送入 LLM

  示例遍历：
    Transformer ──[启发]──→ BERT
       │                      │
       ├──[启发]──→ GPT         ├──[改进]──→ RoBERTa
       │                      │
       └──[改进]──→ ViT        └──[改进]──→ ALBERT

  → LLM 不仅看到 Transformer 本身，还能看到完整的演化关系链

主要优势：
  - 多跳推理：沿关系路径连接分散的知识（传统 RAG 容易漏掉跨跳关联）
  - 关系感知：不仅是语义相似，还知道实体之间的具体关系类型（因果/继承/对比）
  - 结构化约束：图谱可以施加领域知识约束（如"只考虑药物-疾病治疗关系"）
  - 可解释性：检索路径可视，回答来源可追溯

主要方法：
  ┌─────────────────────────────────────────────────────────────┐
  │ 方法              │ 核心思路                       │ 代表作     │
  ├─────────────────────────────────────────────────────────────┤
  │ KG + RAG          │ 用知识图谱补充向量检索          │ KnowledGPT │
  │ Graph RAG         │ 图谱索引 + 社区摘要            │ Microsoft  │
  │ GRAG              │ 图结构检索 + 关系约束          │ 2024       │
  │ LightRAG          │ 轻量级图 RAG，增量更新         │ 2024       │
  │ HybrID RAG        │ 向量 + 图谱双通道融合          │            │
  └─────────────────────────────────────────────────────────────┘

挑战：
  - 实体抽取的质量直接影响图谱质量（错误传播）
  - 图遍历的开销随深度指数增长
  - 动态更新图谱比更新向量库更复杂
  - 复杂长尾关系难以完整覆盖

适用场景：
  - 多跳推理问题（科研文献追溯、法律条款推导）
  - 强关系型知识（药物-靶点、供应链、组织架构）
  - 需要结构化可追溯回答的场景
```

## 十、局限性

### 10.1 已知问题

| 问题                     | 表现                       | 缓解方案               |
| ------------------------ | -------------------------- | ---------------------- |
| **检索失败**       | 相关文档没找到             | 查询改写、多路检索     |
| **上下文注入偏差** | LLM 过度依赖或不依赖上下文 | 精心设计 Prompt        |
| **信息冗余**       | 多个 chunk 信息重复        | MMR 去重、压缩         |
| **知识冲突**       | 检索结果之间矛盾           | 置信度评分、多数裁决   |
| **时效性问题**     | 索引中的知识过期           | 定期更新索引           |
| **长尾实体**       | 低频实体 embedding 质量差  | 实体链接、知识图谱融合 |

### 10.2 部署陷阱

```text
陷阱 1：Embedding 模型不一致
  索引时用 text-embedding-3-small，检索时用 bge-large
  → 向量空间不匹配，检索质量断崖下降

陷阱 2：分块策略与检索策略不匹配
  分块 2000 tokens 但用精确匹配检索
  → 核心信息被淹没在大量噪声中

陷阱 3：忽略元数据过滤
  所有知识放到同一个集合中，没有按时间/类型/来源过滤
  → 过时信息影响回答质量

陷阱 4：不做 Prompt 保护
  检索到的内容可能包含恶意指令
  → 需要上下文消毒（sanitize）

陷阱 5：不做空结果处理
  检索结果为 0 时，LLM 还是会被要求"基于文档回答"
  → 要么幻觉，要么无回答，应该优雅降级
```

### 10.3 适用场景矩阵

```text
                    RAG 适用性对比

               强烈推荐             有条件使用         不推荐

实时知识更新    ✅ 新闻/政策        ✅ 周更新数据
长尾专业领域    ✅ 法律/医疗文档    ✅ 内部知识库
高可解释性      ✅ 合规/金融        ✅ 客服系统
大规模知识库    ✅ 万级以上文档      ✅ 千级文档
                                  ❌ 百级文档 → 直接注入 Prompt
纯创意生成      ❌ 写诗/故事        ❌ RAG 不适合发散性创作
高频低延迟      ❌ 毫秒级要求        ✅ 可以预缓存热点查询
```

```text
RAG 系统规划检查清单：

知识库：
  □ 总文档数
  □ 文档格式（PDF/MD/HTML/DB/...）
  □ 更新频率（实时/每日/每周/静态）
```
