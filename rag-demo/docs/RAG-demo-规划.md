# 基于 `知识库.md` 的 RAG 全流程 Demo 规划

> 目标：用一份小型中文知识库，搭建一个能跑通“文档接入 -> 切分 -> 向量化 -> 检索 -> 重排 -> 组装上下文 -> 生成答案 -> 返回引用”的完整 RAG Demo。

这份规划不是直接写代码，而是把 demo 的设计、模块、流程和验收标准先定下来，方便后续按模块实现。

---

## 1. Demo 定位

这份知识库是关于“创新学社”的介绍文档，内容包含：

- 社团定位与价值观
- 加入流程与考核方式
- 学习路径与科研资源
- 校园生活、宿舍、军训、图书馆、餐饮等生活信息
- 勋章机制、分享会要求、人员要求

它的特点是：

- **单文件但主题多**：适合测试分块和检索精度。
- **中文自然语言为主**：适合测试中文 embedding 和中文问答。
- **结构半松散**：有连续段落，也有明确小标题，适合测试不同切分策略。
- **适合引用**：用户很容易追问“这句话来自哪里”。

因此，这个 demo 最适合做成一个“知识库问答助手”，重点验证：

1. 能不能正确找到相关段落
2. 能不能把长文档切得合理
3. 能不能回答得忠实、简洁、可追溯
4. 能不能区分知识库内问题和知识库外问题

---

## 2. Demo 目标

### 2.1 核心目标

做出一个最小但完整的 RAG 闭环：

```text
知识库.md
-> 文本解析
-> Chunk 切分
-> Embedding
-> 向量检索
-> 可选关键词检索
-> 重排
-> 上下文拼装
-> LLM 生成
-> 引用返回
```

### 2.2 体验目标

用户在界面上可以：

- 上传或加载 `知识库.md`
- 输入问题
- 看到系统检索到了哪些片段
- 看到最终答案
- 看到答案对应的引用来源
- 看见“知识库没有覆盖”的兜底回答

### 2.3 质量目标

这个 demo 不追求大而全，优先追求：

- 回答准确
- 引用清晰
- 实现可拆分
- 方便后续替换模型和向量库

### 3.1 事实型问题

## 4. Demo 总体架构

建议采用 5 层结构：

1. **数据层**
   - 读取 `知识库.md`
   - 解析文本
   - 保留标题、段落、序号

2. **索引层**
   - 文本切分
   - 生成 embedding
   - 写入向量库

3. **检索层**
   - 用户问题改写
   - 向量检索
   - 可选 BM25 混合检索
   - rerank

4. **生成层**
   - 组装上下文
   - 构造 prompt
   - 调用 LLM
   - 返回答案和引用

5. **展示层**
   - Web 页面或简单聊天页
   - 显示检索片段
   - 显示答案来源
   - 显示调试信息

## 5. 文档切分方案

这份知识库本身是一个长 Markdown 文档，而且内部已经有大量语义块。切分策略建议分两层。

### 5.1 第一层：按标题结构切

优先按 Markdown 逻辑块切分，比如：

- 社团介绍
- 报到与宿舍生活
- 必备物品
- 校园美食
- 学习方法与考试策略
- 科研与长期规划
- 图书馆与资源利用
- 军训与健康小贴士
- 职业发展
- 加入方式
- 学习资料
- 勋章机制
- 分享会要求
- 人员要求
- 筛选原则/考核方式

这样可以保证每个 chunk 有比较完整的主题。

### 5.2 第二层：段落内再细分

如果某个标题下内容过长，再按段落或句子细分，避免 chunk 太大。

建议：

- chunk 目标长度：300 到 600 中文字左右，或者 200 到 500 tokens
- overlap：50 到 100 中文字

### 5.3 切分原则

1. 尽量不切断一个完整规则或流程
2. 尽量保留标题路径
3. 尽量避免把“生活信息”和“学习信息”混在一个 chunk 里
4. 对列表型内容，保留列表前缀和编号

### 5.4 建议的 chunk 元数据

每个 chunk 最好带上：

- `doc_id`
- `chunk_id`
- `title_path`
- `section`
- `source_file`
- `chunk_type`
- `order`

示例：

```json
{
  "doc_id": "knowledge-base-001",
  "chunk_id": "kb-001-07",
  "title_path": ["学习方法与考试/复习策略"],
  "section": "复习策略",
  "source_file": "知识库.md",
  "chunk_type": "paragraph",
  "order": 7
}
```

## 6. 检索方案

这类中文知识库 demo，建议优先做“混合检索 + 重排”。

### 6.1 第一阶段：向量检索

用 embedding 找语义相近的 chunk。

适合问法：

- “学社希望培养什么样的人？”
- “图书馆怎么借书？”
- “勋章分几类？”

### 6.2 第二阶段：关键词检索

用 BM25 或简单关键词匹配补足精确词命中。

适合问法：

- “考核期多久？”
- “无故缺席不得超过几次？”
- “一层通常会有微波炉吗？”

### 6.3 第三阶段：重排

对召回结果做 rerank，优先把真正回答问题的段落放前面。

这一步尤其重要，因为这份知识库主题很多，召回容易把相近主题混在一起。

### 6.4 检索参数建议

- 初召回 `top_k = 10 ~ 20`
- 重排后保留 `top_k = 3 ~ 5`
- 对复杂问题可扩大到 30

### 6.5 检索过滤建议

如果后面还要扩展成多文档知识库，建议提前把过滤接口留好，例如：

- `category`
- `topic`
- `source`
- `version`

目前单文件 demo 可以先不做复杂过滤，但接口要预留。

## 7. Prompt 与回答策略

### 7.1 Prompt 目标

Prompt 要明确让模型：

- 只根据检索到的资料回答
- 找不到资料就明确说“不知道”
- 回答要简洁、准确、可引用
- 尽量不要发散讲太多背景

### 7.2 推荐输出格式

```text
回答：
...

依据：
[1] chunk-03
[2] chunk-07
```

### 7.3 兜底策略

如果检索不到足够相关的内容：

- 先返回“当前知识库中没有找到明确依据”
- 再建议用户换个问法或补充关键词

这样可以显著减少幻觉。

### 7.4 对这份知识库的特殊提示

因为内容里有很多“制度、规则、流程、资源、生活信息”，所以 prompt 最好鼓励模型区分：

- 规则类答案要准确给出限制条件
- 流程类答案要按步骤回答
- 总结类答案要先归纳再展开

## 8. Demo 页面建议

建议做一个最小 Web 页面，包含四个区域：

### 8.1 左侧：知识库加载区

- 显示当前文档名：`知识库.md`
- 显示文档解析状态
- 显示 chunk 数量
- 显示 embedding 是否完成

### 8.2 中间：问答区

- 输入问题
- 点击提问
- 显示最终回答

### 8.3 右侧：检索结果区

- 显示 top-k 召回 chunk
- 每个 chunk 显示标题路径、分数、摘要
- 支持点击展开原文

### 8.4 底部：调试区

- 显示改写后的 query
- 显示 prompt 版本
- 显示模型名称
- 显示 token 用量和响应时间

这样做的好处是：demo 不只是“能答”，还能“看见它怎么答”。

## 9. 数据流设计

建议把 demo 数据流拆成四步：

### 9.1 ingest

读取 `知识库.md`，输出结构化段落。

### 9.2 index

对每个 chunk 生成 embedding，写入向量库。

### 9.3 retrieve

用户提问时，做 query rewrite 和混合检索，返回候选块。

### 9.4 generate

把候选块拼进上下文，调用大模型生成答案。

建议把每一步都存日志，便于调试。

## 10. 推荐技术栈

如果你想快速做一个 demo，可以这样选：

### 10.1 基础版

- 后端：Python + FastAPI
- 文档处理：Markdown 解析 + 自定义切分
- 向量库：FAISS / Chroma / Milvus 任选其一
- embedding：通用中文 embedding 模型
- rerank：轻量 reranker 或直接先不用
- 前端：Streamlit / Gradio / 简单 React 页面

### 10.2 进阶版

- 后端：FastAPI
- 检索：向量检索 + BM25 混合
- 重排：cross-encoder reranker
- 生成：支持流式输出
- 监控：日志 + 检索命中率统计

### 10.3 选择建议

如果目标是“先跑通”，优先：

1. Streamlit + FAISS + embedding + LLM
2. 之后再加 BM25 和 rerank

这样最容易在一天内做出第一版。

## 12. 验收标准

一个 demo 是否合格，可以按下面标准判断。

### 12.1 功能验收

- 能加载 `知识库.md`
- 能完成切分和入库
- 能对中文问题检索到相关 chunk
- 能生成带引用的回答
- 能对知识库外问题做兜底

### 12.2 质量验收

- 回答和原文一致
- 关键限制条件不丢失
- 检索结果大体相关
- 引用能追溯到原始段落

### 12.3 工程验收

- 可重复运行
- 可替换 embedding 模型
- 可替换向量库
- 可查看每一步中间结果

## 13. 分阶段实施路线

### 阶段一：最小闭环

目标：先跑通问答。

实现内容：

- 读入 `知识库.md`
- 简单切分
- embedding
- 向量检索
- LLM 回答

### 阶段二：提高准确率

加入：

- 更合理的标题级切分
- chunk overlap
- 混合检索
- rerank

### 阶段三：提高可解释性

加入：

- chunk 原文展开
- 引用编号
- 检索分数展示
- prompt 和 query 调试信息

### 阶段四：提高稳定性

加入：

- 日志
- 缓存
- 错误兜底
- 评测集

## 15. 我建议的最终 demo 形态

如果要我给一个最稳的版本，我会建议做成：

**“创新学社知识库问答助手”**

6. 展示答案和引用来源
7. 知识库外问题给出明确兜底

## 17. 一句话总结

这份小型知识库最适合做一个“轻量但完整”的 RAG demo：

**用标题级切分保证语义，用混合检索保证召回，用重排保证排序，用引用保证可信，用兜底保证不胡说。**
