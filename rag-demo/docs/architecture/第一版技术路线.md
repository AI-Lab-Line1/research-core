# 第一版技术路线

这份文档记录当前项目第一版的推荐方向。目标不是一次把所有东西做满，而是先做出一个能完整展示 RAG 工作流程的学习型 Demo。

---

## 1. 已确认方向

### 1.1 后端

你已经确认后端使用 `Python3`。

这很适合 RAG Demo，原因是：

- 文档处理生态更成熟
- 向量检索和文本处理资料更多
- 更适合快速搭建原型
- 后续更容易接 embedding、rerank、检索和日志模块

### 1.2 项目目标

第一版重点不是性能，而是“看得懂流程”。

要求是：

- 前后端交互可用
- 浏览器里可以直接问答
- 能展示每一步如何运行
- 能看到不同方法的并列位置
- 先跑通主流程，再逐步补足其它方法

### 1.3 可视化目标

你希望看到的是：

- 原理
- 工作流程
- 每一步怎么衔接
- 不同方法的差异

你不希望第一版就陷入特别深入的数据细节。

这意味着可视化应该偏“流程演示型”，不是“数据分析型”。

---

## 2. 前端方案对比

### 2.1 轻量原型方案

例如：Streamlit、Gradio、简单模板页。

#### 优点

- 上手快
- 适合快速验证 RAG 流程是否可跑通
- 开发成本低
- 比较适合早期内部试验

#### 缺点

- 布局和交互能力有限
- 不太适合复杂的多面板可视化
- 难以做稳定、精细、长期扩展的前端体验
- 方法对比和流程图展示容易显得简陋

### 2.2 标准前端方案

例如：React、Vue、配合组件库和状态管理。

#### 优点

- 组件化强，适合多模块界面
- 更适合做多方法对比面板
- 更容易做流程图、步骤条、日志面板、检索结果面板
- 后续扩展性好
- 更像一个真正可以给别人演示的浏览器产品

#### 缺点

- 初始工程搭建比轻量原型复杂
- 组件、路由、状态管理需要前置设计
- 开发速度在第一天不一定最快

### 2.3 推荐结论

如果目标是“先快速证明流程”，轻量原型更快。

如果目标是“做一个能展示给别人看的完整学习型 Demo”，标准前端更合适。

**结合你的目标，我推荐标准前端方案。**

如果只让我在 React 和 Vue 之间选，我会更偏向 React + TypeScript，理由是：

- 生态更丰富
- 复杂可视化和组件组合更常见
- 适合做多页面、多个步骤面板、对比视图

不过这不是硬性结论。如果你更熟 Vue，也可以用 Vue。第一版的重点是流程，不是框架宗教。

---

## 3. 第一版推荐组合

### 3.1 推荐栈

- 前端：React + TypeScript
- 后端：Python3
- 接口层：REST API 风格即可
- 任务目标：先跑通完整流程，再补充方法分支

### 3.2 第一版的目标形态

第一版建议做成：

```text
浏览器前端
-> 选择方法
-> 上传/加载知识库
-> 触发切分
-> 触发索引构建
-> 输入问题
-> 检索
-> 生成
-> 展示答案和流程
```

这条主线必须跑通。

---

## 4. 第一版方法范围

你希望先用一套推荐方案把完整流程跑通，同时把其它并列方法留空位，后面再补充。

我建议第一版按“一个主方案 + 两个并列占位方案”的方式设计。

### 4.1 主方案：基线 RAG

这是第一版真正跑通的方案。

组成建议：

- 标题/段落切分
- 向量检索
- 简单上下文拼装
- LLM 生成
- 引用返回

这个方案负责把整条链路先打通。

### 4.2 并列方案 A：固定长度切分版

这是第一个对照组。

用途：

- 用来对比不同切分策略的差异
- 让用户看到“切分方式不同，召回结果会不同”

### 4.3 并列方案 B：混合检索增强版

这是第二个对照组。

用途：

- 用来对比向量检索和关键词检索的差异
- 让用户看到“召回和排序是两件事”

### 4.4 后续预留的增强位

后面可以再补：

- rerank
- query rewrite
- context compression
- multi-turn RAG
- graph RAG

但第一版先不强行全上。

---

## 5. 第一版要预留的空缺

你提到要把各个模块并列的地方空缺出来，这个思路是对的。

建议第一版先把这些位置预留成统一接口：

1. **切分策略接口**
   - 固定长度切分
   - 标题结构切分
   - 后续可插入语义切分

2. **检索策略接口**
   - 向量检索
   - 关键词检索
   - 混合检索

3. **排序策略接口**
   - 直接按相似度
   - rerank
   - 后续可插规则加权

4. **上下文构造接口**
   - 基础拼装
   - 压缩版
   - 带引用版

5. **生成策略接口**
   - 直接回答
   - 证据优先回答
   - 无答案兜底回答

这样后面补方法时，不用重构主流程。

---

## 6. 第一版可视化重点

第一版可视化建议聚焦流程，不深入复杂数据细节。

重点展示：

- 文档从哪里来
- 被切成了哪些块
- 每种方法的 chunk 长什么样
- 检索命中了哪些块
- 哪些块被送进上下文
- 最终答案怎么来的

不建议第一版强行展开：

- embedding 数值细节
- 向量高维分布分析
- 复杂模型参数调优
- 深层检索算法数学细节

因为你的目标是展示原理和工作流程，不是做学术分析。

---

## 7. 当前阶段的实施顺序

建议按这个顺序推进：

1. 固定项目目录结构
2. 明确前端与后端边界
3. 设计统一的 pipeline 数据结构
4. 先实现主方案的完整流程
5. 再补充对照组方法
6. 最后补前端可视化页面

---

## 8. 结论

当前最稳妥的第一版方向是：

- 后端用 Python3
- 前端用标准前端方案
- 主线先跑通一个基线 RAG
- 旁路方法先留接口，不急着全实现
- 可视化重点放在流程和方法对比

这能满足“先能展示、再能学习、最后再扩展”的目标。
