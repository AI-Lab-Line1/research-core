# 结构化生成说明

## 1. 为什么第一版经常只有一句话

第一版生成器只做句子级关键词覆盖：

1. 将召回的 chunk 按句号切成句子。
2. 保留包含查询词的句子。
3. 按查询词覆盖率和检索分数排序。
4. 过滤没有增加新查询词的低分句子。

这会产生两个典型问题：

- “创新学社有哪些勋章”中，概述句已经包含“创新学社”和“勋章”，真正包含五类勋章的枚举句反而可能被过滤。
- “加入学社的流程”中，其他包含“学社、经过”等常见词的句子可能混入答案。

前端并没有裁剪答案。信息缺失发生在生成器选句阶段。

## 2. 新的数据流

```text
问题
  -> 意图识别
  -> 查询词与主题词分离
  -> 证据 chunk 按句切分
  -> 候选句打分
  -> 枚举 / 流程结构解析
  -> AnswerPoint 列表
  -> 前端逐条展示引用与入选原因
```

每个 `AnswerPoint` 包含：

```text
text               答案点正文
citation           在当前上下文中的引用编号
chunk_id           来源 chunk
selection_reason   为什么选择这一条
```

## 3. 意图识别

当前识别四类问题：

| 意图 | 常见问法 | 输出方式 |
| --- | --- | --- |
| `list` | 哪些、哪几种、分类、类型 | 枚举列表 |
| `process` | 流程、步骤、如何加入 | 有序步骤 |
| `fact` | 多少、什么时候、多久、是否 | 多条事实 |
| `general` | 其他综合问题 | 证据要点 |

如果证据分数或主题词覆盖率不足，输出意图会变成 `fallback`。

## 4. 主题词分离

“加入学社需要经过哪些流程”经过分词后可能包含：

```text
加入 / 学社 / 需要 / 经过 / 流程
```

其中“学社、需要、经过、流程”区分主题的能力很弱。生成器将它们视作通用问题词，核心主题词只保留“加入”。候选句必须命中主题词，因此包含“经过严格评议”的勋章句不会再混入加入流程。

## 5. 候选句打分

当前候选句分数由四部分组成：

```text
score =
    0.50 * topic_term_coverage
  + 0.15 * query_term_coverage
  + 0.20 * normalized_retrieval_score
  + 0.45 * structure_signal
```

`structure_signal` 只在句子符合当前问题意图时添加。例如：

- 枚举问题遇到“分为、包括、包含、分别是”
- 流程问题遇到“加入方式、步骤、首先、然后、→”

这个分数只用于教学型选句，不是训练得到的概率。

## 6. 结构解析

### 6.1 枚举

原始证据：

```text
勋章分为特别勋章、技术勋章、宣传勋章、组织勋章和学社勋章。
```

解析结果为五个独立答案点，每一项保留相同来源引用。

### 6.2 流程

原始证据：

```text
加入方式：扫码加入面试群 → 填写报名表 → 完成一个月考核期 → 成为正式成员。
```

生成器按箭头拆成四个有序步骤。前端不再把整个流程挤在一个句子中。

### 6.3 事实

事实问题不强制结构解析，而是选择覆盖不同主题词的证据句。例如开放时间和借阅数量会成为两个答案点。

## 7. Trace 中可以看到什么

`generate` 阶段现在包含：

```text
detected_intent
output_intent
query_terms
topic_terms
candidate_sentence_count
selected_points
llm_called = false
```

因此可以从 Trace 中解释为什么某个句子入选、问题被识别成什么类型，以及是否因为证据不足进入兜底。

## 8. 当前边界

这仍然是规则生成器：

- 只认识预设的中文问法和结构词
- 复杂枚举格式可能无法正确拆分
- 不能像 LLM 一样改写、归纳或跨多段推理
- 主题词过滤依赖分词结果和通用词表

它的价值是行为确定、无需模型、每一步都能展示。当前 LongCat-2.0 已作为并列生成方法接入，这套规则生成器继续作为可复现的基线方法进行对比。
